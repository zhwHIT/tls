# 日期证据瓶颈诊断与两阶段优化

> 本文为逐轮历史记录。三主题最终结果、停止原因及后续 v8.4 上下文去重验收见 [45_授权实测结果与覆盖优化验收](45_授权实测结果与覆盖优化验收.md)。最终本地测试 262 项通过，尚未整体达到 70% 日期召回目标。

日期：2026-09-14。用户已明确授权完整轨迹外发，并要求分析、实施优化及验证严格 gold 日期覆盖变化。

## 状态

已完成代码优化、235 项离线测试，以及真实已检索片段的时间标注契约检查；优化后的三主题串行批次已启动。本文先记录原因和实现，实际结果待运行结束后补充，不能把日期可用性分析当成生成效果。

批次目录：`chronos_repro/artifacts/tisa_v8_temporal_batch_01/`。输出仍使用各主题原目录，以保留累计请求账本；历史结果在每次重放前归档。

## 1. 优化前观察到了什么

### 1.1 已有失败轨迹的损失分析

分析源为归档的 Yemen 轨迹：`chronos_repro/artifacts/tisa_v7_diagnostic/crisis_yemen/history/20260914T130120-a6182b77/trajectory.json`。

| 环节 | 实际观察 |
| --- | --- |
| 检索 | 7 次 SEARCH，56 个选中片段 |
| VERIFY | 共 434 条候选，415 条 INSUFFICIENT，19 条 SUPPORTED |
| 日期精度 | 366 条没有日期，49 条为年/月等部分日期，19 条为完整日期 |
| 验证后日期 | 17 个不同日期，命中 gold 5/81 |
| 最终日期 | 同为 17 个不同日期，命中 gold 5/81 |
| MERGE | 17 次 APPEND、2 次 UPDATE；没有已通过验证的 gold 日期在合并后丢失 |

因此，已观察到的主要损失在选段和日期证据，而不是 MERGE 删除了大量正确日期。字面日期扫描只是诊断特征，不构成事件覆盖的上界或语义判断。

报告：`chronos_repro/artifacts/yemen_before_hardening_funnel.json`。

### 1.2 原框架没有接入现成时间标注

冻结文件 `articles.preprocessed.jsonl.gz` 已包含句子与 token 级 `time`、`time_format`。例如文章发布于 2011-01-15，其中 yesterday 已标注为 2011-01-14。原检索层只传递正文，原 VERIFY 只接受字面完整日期，因此大量含相对日期的新闻事件被保留为 INSUFFICIENT。

在原 56 个片段中，离线探测找到 152 个完整精度的归一化标注，标注日期涉及 13 个 gold 日期。**这是标注日期的可用性，不是生成了 13 个正确事件。** 探测还发现 `last days` 被上游标成单日等问题，不能盲目信任预处理输出。

报告：`chronos_repro/artifacts/yemen_frozen_timex_probe.json`。

### 1.3 高强度默认思考带来额外开销

首次授权启动的 hardening1 重放中，两次 VERIFY 分别使用 11,085 和 15,279 reasoning tokens，但仍遇到相同日期证据限制。客户端没有明确设置思考开关；官方文档说明默认启用 thinking，默认 effort 为 high。[DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

为避免继续消耗同类低效调用，主动停止该批次，保留 checkpoint、缓存和账本。累计请求从 77 增至 87；包含中断时已经预留的请求，不能把所有请求都当成正常返回或确定已计费。该实验是 **interrupted_for_measured_optimization**，不是完整运行、模型失败或余额不足。

批次原记录：`chronos_repro/artifacts/tisa_v7_hardening_batch_01/batch_status.json`。

## 2. 借鉴哪些论文，哪些没有照搬

### DATEWISE：利用时间表达，而非只寻找字面 YYYY-MM-DD

论文用 HeidelTime 识别和解析文本中的日期表达，并将日期选择与日期摘要组织起来。这支持接入已有冻结时间标注的工程方向，但不意味着可把发布时间直接复制为事件日期。[Examining the State-of-the-Art in News Timeline Summarization](https://aclanthology.org/2020.acl-main.122/)

### MAS-TLS：相关性与时间覆盖共同决定证据分配

论文通过覆盖与多样性目标分配证据，减少反复集中在同类时间段。本次只借鉴“给尚未覆盖的时间证据一个小幅增益”，未引入多 agent 委员会，仍保持原两阶段控制器。[Agent Newsroom / MAS-TLS](https://aclanthology.org/2026.acl-long.1149/)

### CHRONOS：保留迭代检索和短片段

CHRONOS 闭域实验使用 Elasticsearch，并将文档切成约 500 词的片段。本框架已有 500 词切分及 3200 字符上限，不以增加完整文档上下文解决问题；继续保留 query→检索→验证→合并的迭代结构。[CHRONOS](https://aclanthology.org/2025.findings-naacl.248/)

上述借鉴是本项目的实现取舍，不是对论文完整方法的复现，也不直接沿用论文指标数值作比较。

## 3. 已实施的优化

### 3.1 原文绑定的 temporal_annotations

新增 `chronos_repro/src/chronos_repro/frozen_timex.py`。

读取当前主题冻结预处理文件，不访问 gold。将 token 标注重新映射到原始正文字符位置，保留原文哈希、起止位置、原始表达、归一化日期和来源规则。

采用白名单：完整字面日期、一致的 today/yesterday、与日期和星期相符的近期 weekday、满足限制的字面月日。拒绝不一致日期、模糊短语和不满足精度的标注。不是重新运行大模型日期猜测，也不把预处理结果直接当作事件真值。

每个片段最多提供 12 条标注，LLM 输入仅保留 annotation_id、expression、date、rule 及发布时间锚点；完整哈希和位置留在程序端。

### 3.2 VERIFY 接受两种可审计日期来源

1. 原有字面完整日期证据。
2. 当前片段中明确提供、且通过检查的冻结时间标注。

使用第二种来源时，模型必须引用 annotation_id、相同表达和日期，并提供包围该表达实际位置的事件原文。程序再次检查 ID、哈希、位置、归一化规则、发布时间锚点及引用范围。

即使有标注，模型仍须判断表达是否确实修饰该事件；泛指每周活动、计划与已发生事实、矛盾日期均不能自动转成 SUPPORTED。来源契约检查不是独立的语义蕴含评测。

### 3.3 两阶段 memory 和选段

第一阶段继续维护全局骨架，但额外提供：

- 最多 6 条开放的待核实线索，而不是把全部候选塞进上下文。
- 从冻结索引统计的文章发布年份分布，明确其只是语料可用性，不是事件起止边界。

这不是添加 Egypt 等主题的人工议程，也没有把 gold 缺少的年份写入输入。模型仍自主生成 query，只要求优先跟随已有证据，避免无依据地扩展到语料中缺乏支持的时期。

选段仍以相关性、文档多样性和重复度为主，对相关片段中的新日期标注加入小幅软增益。不强制均匀日期，不按 gold 日期检索，不删除相邻日期。

第二阶段继续局部 gap 修复，保留 SEARCH / VERIFY / MERGE / STOP 和 GAP_MEMORY，不改为全局长上下文反复生成。

### 3.4 控制模型输出和缓存

新增 `chronos_repro/src/chronos_repro/runtime_profile.py`，版本为 `two-phase-v8-temporal-grounding`，记录：

- `thinking: {type: disabled}`；模型仍输出短的行动理由 thought，而不是长内部推理。
- 单次 `max_tokens=8192`。
- 每批候选数额外限制为 12，仍允许分页抽取。
- 每片段最多 12 条时间标注；全局策略最多 6 条待核实线索。

思考开关和输出上限加入 API 缓存键，避免错误复用旧推理配置的输出。运行记录与代码指纹包含这些参数，没有修改累计授权上限。

全局请求仍有 64,000 字符保护；该值不是 tokenizer token 上限，更不证明 Qwen 训练时不会 OOM。真实 tokenizer 和显存测试仍需单独完成。

## 6. 实际生成结果

### v8.0 中间实验，不是完整结果

`tisa_v8_temporal_batch_01` 在首批 VERIFY 的逐字引用校验中失败，累计账本增至 91。随后加入逐候选隔离机制：保留通过原验证器的候选，隔离无效候选及原始输出；修复耗尽的 VERIFY 步骤不作为训练正例。

`tisa_v8_temporal_batch_02` 进行 1 次 SEARCH，生成 28 个事件、21 个不同日期，严格命中 6/81（7.41%），相比旧版 5/81 有数值增加，但在 MEMORY_UPDATE 引用 event ID 而非 passage ID 时停止。累计请求增至 131；MJ 与 David Bowie 尚未启动。

报告：`chronos_repro/artifacts/yemen_v8_0_intermediate_funnel.json`。

进一步人工检查发现，这一版本存在来源时间标注的年份错误：文档 3199 是发表于 2012-02-20 的回顾时间线，正文先有 January 29, 2011，随后 April/May/June 等沿用 2011 年；上游却给部分日期填了 2012 年。**因此不能把这个 7.41% 当成优化已完成或生成质量已可靠的结论。** 132 个来源契约检查通过并不能排除这种语义/年份错误。

### v8.1 已修复上述问题并重新测试

- 结构化日期标题之间继承明确写出的年份，不从发布时间继承；跨年回退但没有新年份锚点时拒绝推断。
- 时间标注向模型提供最多 180 字符的原文引用提示和短年份依据，减少逐字复制失败。
- 标注窗口仍最多 12 条，但重访时优先提供尚未进入时间线的日期，避免首批标注永久遮蔽后续日期。
- MEMORY_UPDATE 允许引用当前可见的 verified event ID，由程序映射回已有 passage 来源；不存在或没有来源的 ID 仍拒绝。没有把 event ID 当作无条件证据。
- 第一阶段只做一页主要节点抽取；第二阶段最多两页。修复耗尽的批次不立即反复分页，未完成抽取仍记录为未完成。
- 代码版本 `two-phase-v8.1-source-year-coarse-pass`，全量测试 **242 passed in 8.83s**。

批次：`chronos_repro/artifacts/tisa_v81_temporal_batch_01/`。从 Yemen 累计 131 次请求开始，在第 4 次 SEARCH 后的 MEMORY_UPDATE 失败，累计 185 次；其他两主题尚未调用。

中断时：80 个事件、61 个不同日期，严格日期命中 **14/81（17.28%）**。相比原始中断基线 5/81 有增加，但仍未完成第一阶段，更未完成两阶段，不能作为最终效果。

原因：合并后 memory 的 objective 要求 `observations=[]`，但继承的 `required_json` 示例仍要求抽取带日期/原文的 observations。模型遵循了冲突示例，重复抽取后触发时间表达引用错误。另观察到第一阶段连续追逐 Abyan、捐款等细节线索，没有优先检查全局起点。

### v8.2：消除 prompt 契约冲突，明确粗粒度优先

- 新增专门的 post-merge memory prompt，示例和输出上限都将 observations、discovered_keywords 固定为空。
- 校验先检查不可重复抽取，再校验骨架，避免 repair 被无关的原文引用错误带偏。
- 策略与 memory 均明确优先起止边界、缺失的大阶段；开放细节线索留给第二阶段，不需要第一阶段耗尽。没有添加主题专属议程或 gold 信息。
- 日期证据和来源校验没有放宽。两个阶段、工具动作和上下文边界保持不变。
- 全量本地测试：**245 passed in 7.88s**。
- 新批次：`chronos_repro/artifacts/tisa_v82_temporal_batch_01/`；从 Yemen 累计 185 次开始，剩余 215 次，不重置账本。

离线漏斗报告补充标注日期可见性和严格日期 precision/F1。日期可见性只诊断检索/抽取损失，不能等同于事件正确性；基于多参考日期并集的精确率也不意味着参考之外的事件一定错误。

### Windows checkpoint 替换失败修复

v8.2 第一批次在第二次 SEARCH 后因 `checkpoint.tmp -> checkpoint.json` 的 Windows `PermissionError: WinError 5` 中断，累计请求 207。可能是监测读取或其他短暂文件占用；日志只能证明替换被拒，不能唯一确定占用进程。

对 checkpoint、请求账本、API 缓存和批次状态的原子替换加入最多 8 次、总等待约 3.55 秒的本地退避。只重试 PermissionError；文件不存在等错误直接失败，持续拒绝访问仍停止，不吞错。重试文件替换本身不会再次调用 API。

全量测试 **248 passed in 8.21s**。再次启动 `tisa_v82_temporal_batch_02`，保留累计 207 次账本及已有响应缓存，剩余 193 次。运行源码与输入消息已绑定；此次仅 I/O 修复，不修改策略或模型参数，相同请求可复用缓存。这仍是从头缓存重放，不是真正 checkpoint 续跑。

### 上一轮额外诊断

v8.1 标注可见 gold 日期 21 个，VERIFY 接受 17 个，MERGE 后 14 个。三个被合并/丢弃的日期分别涉及冲突开始与翌日进展、计划选举与宣布计划、抵达治疗与已在治疗的状态；需逐项判断，不能为增加日期数一律 APPEND。

v8.1 已返回 API 响应中，策略输入最大 5,580 tokens，memory 最大 7,875 tokens，VERIFY 最大 6,929 tokens；全部请求最大 34,948 字符。这里只是 DeepSeek tokenizer 统计且来自中断轨迹，未来 Qwen 的 tokenizer、输入加输出总长度和显存仍需实际验证。

报告：`yemen_v81_intermediate_funnel.json`、`yemen_v81_context_report.json`；均在 `chronos_repro/artifacts/`，离线生成，0 次 API。

### v8.2 实际结果与 v8.3 停滞交接

`tisa_v82_temporal_batch_02` 完成第一阶段 6 次 SEARCH / 60 步，86 个事件、65 个不同日期，严格命中 **24/81（29.63%）**。第 7 次策略决策因重复已有 query，经过两次修复仍无效而停止。累计请求为 280；未进入第二阶段，不是完整成功。

行为上，模型开始主动搜索早期背景与后期过渡，而非只追单个细节；但 memory 仍把“多次搜索尚未确认的边界”写成“未搜索”。全局新增事件不能说明某个检索意图得到回答，这需要后续单独的意图进度建模。

v8.3 增加保守的停滞交接：只有最低探索轮数、事件数、阶段数及 EARLIER/LATER 探索条件已经满足，且错误明确是重复 query 修复耗尽，才转入 GAP_REFINEMENT。其他校验失败仍报错。交接记录 `policy_stall_handoff`、`forced=true`、`skeleton_complete=false`，保留原始无效输出与审计；不伪装成模型自主 STOP，不作为 SFT 正例。

第二阶段每次最多精读 4 个相关片段，仍按每批 2 个、最多两页抽取，允许后续再次搜索补充。第一阶段维持 8 个，模型、冻结语料、gold 隔离和总授权上限不变。这是上下文/调用成本取舍，需要用最终覆盖验证，而不是保证不会漏事件。

全量测试：**251 passed in 7.41s**。启动 `tisa_v83_temporal_batch_01`，从累计 280 次请求开始，剩余 120 次。前六轮消息未改，可通过缓存重放恢复；真正断点续跑仍未实现。
