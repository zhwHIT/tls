# 三数据集全量混合索引与性能优化

> 完成日期：2026-09-09
> 环境：Conda `tls`，Python 3.10
> 结论：T17、Crisis、Entities 的 BM25 + 多语言稠密混合索引已全部构建并通过完整性校验。

## 1. 为什么要重构

原 BM25 对英文实体词和精确短语有效，但中文查询检索英文语料时可能完全没有候选。原始稠密方案把全文切成 600 字符、重叠 100 字符的滑窗，三套语料预计产生约 84.2 万个向量；当前 CPU 环境的实测速度意味着构建可能超过一天。该开销会拖慢数据标注、参数消融和 Search Agent 多轮 rollout。

本轮目标不是改变 Agent 的学习任务，而是提供一个冻结、可复现、速度足够的证据环境：Agent 仍学习 SEARCH/STOP、query 和 memory；检索器固定提供 BM25 与多语言语义候选。

## 2. 最终索引方案

### 2.1 双通道

- BM25：SQLite FTS5，索引完整标题和正文，负责实体、日期、短语等词面信号。
- Dense：`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`，384 维，支持中文查询和英文文档的跨语言匹配。
- Fusion：默认使用 weighted RRF，BM25/dense 权重均为 1.0，`rrf_k=60`；保留各通道原始排名和分数，便于消融。

### 2.2 紧凑文档表示

默认每篇文章只生成一个稠密向量，输入由标题以及正文开头、中部、结尾三个分层片段构成，每段总长度受限。BM25 仍看全文，因此紧凑表示不会取消全文词面匹配。完整滑窗可通过 `--max-chunks-per-document 0` 启用，保留作为效果/成本消融。

采用这一策略后，向量总数从预计约 84.2 万降为 72,959，降低约 91.3%。T17/mj 的发布时间代理 pilot 中，紧凑表示没有劣于完整滑窗，但发布时间命中只用于诊断，不能代替真正的 event--passage Evidence Recall。

### 2.3 ONNX 与存储优化

所有依赖均在 `tls` 环境通过清华源安装。模型使用动态 INT8 AVX2 ONNX 推理，向量归一化后以 float16 保存。

- ONNX 文件：`models/paraphrase-multilingual-MiniLM-L12-v2/onnx/model_avx2.onnx`
- SHA-256：`7922812C5B419DEB6AAF352F0B30E0E2B25E4A4C9B84BAC6A945372E8ACE41A2`
- 模型 revision：`e8f8c211226b894fcb81acc59f3b34ba3efd5f42`
- 256 条真实 passage：PyTorch 7.62 条/秒，ONNX INT8 13.05 条/秒，加速 1.71 倍。
- 两后端向量余弦一致性：均值 0.993227，最小值 0.980402。
- 批大小实测后固定为 256。

Sentence Transformers 的[推理后端文档](https://www.sbert.net/docs/sentence_transformer/usage/efficiency.html)说明 ONNX 可用于 CPU 加速，[量化接口文档](https://www.sbert.net/docs/package_reference/util/quantization.html)提供动态量化方法；这里将导出的量化文件与固定 revision 一起保存，避免运行时联网或模型漂移。冻结模型的结构和语言覆盖可查阅其[官方模型卡](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2)。

## 3. 可恢复的 topic 分片构建

稠密索引不再是一个不可中断的大文件，而是按 topic 构建：

1. 读取已有 BM25 索引及 topic 清单；
2. 只加载一次冻结编码器；
3. 每个 topic 编码后先写临时目录，完整成功后再原子发布；
4. 每完成一个 topic 更新根 `manifest.json`；
5. 重跑时校验并跳过已有分片；
6. 查询时根据 `search_engine` 的 topic 只加载对应分片。

因此中断不会损坏已完成 topic，也不需要从第一个 topic 重新开始。T17 的真实 resume 验证成功跳过全部 9 个分片。

| T17 | 9 | 4,203 | 4,203 | 6.23 MiB | 8.53 分钟 |
| Crisis | 4 | 17,573 | 17,573 | 26.34 MiB | 27.66 分钟 |
| Entities | 47 | 51,183 | 51,183 | 78.73 MiB | 76.31 分钟 |

完整验证逐分片检查了 JSONL 行数、向量矩阵形状、float16 类型、有限值和非零向量；结果为 3/3 collection、60/60 topic 全部有效，向量数与 BM25 文档数完全一致。

## 5. 查询性能与功能验证

使用同一持久 Python 进程分别进行首次查询和重复查询：

| 数据集/topic | 查询 | top-k | 首次查询 | 热查询 | 通道情况 |
|---|---|---:|---:|---:|---|
| T17/mj | 中文“迈克尔杰克逊 去世 葬礼 纪念” | 20 | 57.30 秒 | 0.033 秒 | BM25 为 0，dense 提供 20 条 |
| Crisis/egypt | `Mubarak resignation` | 20 | 1.62 秒 | 0.262 秒 | BM25 与 dense 均贡献 |
| Entities/David_Bowie | `David Bowie album health death` | 20 | 4.02 秒 | 0.567 秒 | 20 条均有双通道信号 |

T17 的首次 57.30 秒包含进程第一次加载 ONNX 模型；随后模型复用。三组重复查询的 top 文档 ID 完全一致，说明运行结果可重放。正式批量标注必须使用持久 worker，不应为每个 query 新建 Python 进程。

## 6. 产物与文件作用

核心配置与代码：

- `configs/hybrid_retrieval_v3.json`：生产索引参数、冻结模型、紧凑表示和 RRF 边界。
- `src/chronos_repro/dense_retrieval.py`：ONNX 编码、分层取样、分片构建、resume 和稠密搜索。
- `src/chronos_repro/retrieval.py`：BM25、dense 以及 weighted RRF 的统一入口。
- `scripts/validate_dense_collections.py`：全量索引结构与数值校验。
- `scripts/benchmark_hybrid_indexes.py`：三数据集真实查询的冷/热性能测试。

本地索引与报告：

- `artifacts/t17_dense_collection_v3/`
- `artifacts/crisis_dense_collection_v3/`
- `artifacts/entities_dense_collection_v3/`
- `artifacts/*_collection_v3_hybrid_index.json`：绑定 BM25 与 dense collection 的小型清单。
- `artifacts/dense_collections_validation_v3.json`：完整性验证报告。
- `artifacts/hybrid_runtime_benchmark_v3.json`：查询性能和通道贡献报告。

大型模型和可再生索引由 `.gitignore` 排除，不提交 Git；代码、配置、构建报告和验证报告用于复现。

## 7. 复现命令

以下命令都在 `D:\paper\chronos_repro` 下执行：

```powershell
conda activate tls
$env:PYTHONPATH = "src"

chronos-repro build-dense-collection `
  --bm25-index artifacts\crisis_ece08f344cc94933.sqlite3 `
  --model models\paraphrase-multilingual-MiniLM-L12-v2 `
  --output artifacts\crisis_dense_collection_v3 `
  --backend onnx --onnx-file onnx/model_avx2.onnx `
  --storage-dtype float16 --batch-size 256 `
  --max-chunks-per-document 1

chronos-repro create-hybrid-index `
  --bm25-index artifacts\crisis_ece08f344cc94933.sqlite3 `
  --dense-index artifacts\crisis_dense_collection_v3 `
  --output artifacts\crisis_collection_v3_hybrid_index.json

python scripts\validate_dense_collections.py `
  --case artifacts\t17_dense_collection_v3 `
  --case artifacts\crisis_dense_collection_v3 `
  --case artifacts\entities_dense_collection_v3 `
  --output artifacts\dense_collections_validation_v3.json
```

如果需要重新安装 ONNX 依赖，必须继续使用清华源：

```powershell
D:\miniforge\envs\tls\python.exe -m pip install `
  "sentence-transformers[onnx]==5.1.2" `
  -i https://pypi.tuna.tsinghua.edu.cn/simple
```

## 8. 当前边界与下一步

索引构建和工程性能问题已经解决，但“检索更快”不等于“最终时间线一定更准”。下一步应在 train/dev 上构建 event--passage 相关性标注，对 BM25、dense、1:1 RRF、词面门控/配额以及完整滑窗进行 Evidence Recall@k 消融，再冻结最佳检索配置供两阶段 Memory Search Agent 标注与训练使用。Gold 不进入运行时检索输入。
