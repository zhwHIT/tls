# 续跑瓶颈分析与 v9.6 本地补强

日期：2026-09-16。用户指令：进一步处理分析。

## 结论

当前主要问题是检索到的证据范围、日期与事件的真实对应关系，以及跨日期事件合并；摘要更新不是本轮请求开销的主要来源。单纯提高请求上限不能保证改善这些问题。

v9.5 仍为 7/9 主题完成，即 **77.78%**。此前聊天中的 87.5% 是计算错误，本次更正。全主题聚合、自主停止及语义正确性尚未验收。

本次完成离线分析和 v9.6 本地代码、prompt 补强，新增 API 请求 **0 次**，原始 v9.4/v9.5 结果不改写。v9.6 未在线运行，不应将旧结果记为新版本效果。

## 一、Haiti、Iraq 为什么耗尽预算

| 指标 | Haiti | Iraq |
|---|---:|---:|
| 本轮新增 HTTP 请求 | 300 | 300 |
| VERIFY 请求 | 151（50.33%） | 140（46.67%） |
| 摘要 FACT_MEMORY 请求 | 9（3.00%） | 11（3.67%） |
| 策略 BATCH_POLICY 请求 | 39 | 36 |
| 已提交第二阶段搜索批次 | 11 | 17 |
| 最后 6 个已提交批次的事件状态变化数 | 2、3、0、0、0、1 | 1、0、7、1、0、2 |

两主题均在一个尚未提交完成的批次内触及请求上限。Iraq 已开始第 18 个第二阶段批次，但不能将“已开始”算作完成。单批包含多条 query、逐片段 VERIFY、MERGE 及修复调用，因此批次数远小于 HTTP 请求数。

Haiti 在后期存在连续三个零变化批次；Iraq 仍间歇新增证据，不能套用相同的停搜结论。Haiti 的 11/11 日期命中也不能成为推理期间的停止条件：Gold 仅用于事后诊断，不进入策略状态。

摘要只占 3%–4% 的新增请求，继续降低摘要频率不会解决主要开销。VERIFY 的大部分开销是实际片段处理，不能全部归咎于格式重试；Haiti、Iraq 的策略格式修复分别涉及 10、8 个额外响应，仍值得后续单独检查。

## 三、与原方案的冲突及本地补强

### 1. 不强制制造 gap

Haiti 的一些 gap 是计划执行或决策后果，具有继续检索的依据；另一些只是“获救者后来怎样”“已报告金额后来是否修订”，现有锚点未必建立了需要追查的悬而未决问题。

已补强 GAP_PROMPT：后续问题应有明确的待定决定、计划、未解决后果或冲突，并且其答案会实质改变时间线。一个已经完成的事件，不自动要求补一段后续故事。仍允许输出空 gap 列表，不按事件数强制产生问题。

### 2. 多查询的增益反馈

新增 `batch_feedback`：每个已提交批次只算一次增益，显示最近 4 批和本阶段连续零变化批次数。新批次进一步区分 APPEND、UPDATE、DELETE 的数量。UPDATE 可能只补证据或改文字，不能自动计作新增语义覆盖。

恢复的部分批次带有 `continued_partial_batch` 标记，其续跑部分为零不能推出整个批次为零。连续零变化只给策略判断参考，不触发强制 STOP，不宣称已经覆盖完整。

### 3. 跨日期合并与日期证据

MERGE prompt 增加事件身份规则和通用示例：不同时点的累计费用、伤亡更新、裁决、宣布与实施通常是独立进展。跨日期 UPDATE 应有“同一次发生、日期被纠正或存在争议”的证据。

VERIFY prompt 补充：报头日期不能直接给讣告中的死亡事件定日；时间注释若与明确的事件关系冲突，须保留 INSUFFICIENT。

这些是提示和反馈补强，不是能证明语义等价的硬校验。现有结构验证仍不能自动判断每次跨日期合并是否正确，须通过新实验验收。
