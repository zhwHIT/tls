## 2. 优先级最高：轨迹输入会被后续状态修改

**已确认代码缺陷，影响审计和训练材料可信度。**

- `model_step()` 将 `visible_input` 直接存入轨迹，没有深拷贝。
- `review_gap()` 将可变的 `gap` 对象放入 payload；请求完成后以及后续搜索中继续更新该对象。
- Egypt `step-001` 的 GAP_MEMORY 输入最终记为 `DEFERRED`、已尝试 3 个 query，但随后 `step-004` 的 SEARCH 输入是 `OPEN`、已尝试 0 个 query。后续信息已经回写到先前步骤。
- 本地隔离执行原 `model_step` 函数后修改输入对象，历史记录同步变化，复现成立。

因此不能把这类 `model_input` 直接当成模型当时看到的真实输入。这个问题不等于所有 SEARCH 输入都已污染：策略视图已有部分深拷贝，需要逐类检查。Egypt 的训练门禁仍为 false，仅导出 1 条控制器候选；强制 STOP 不应当成自主停止的训练目标。

**建议下一版**：在记录边界深拷贝输入、输出与观察值；用含后续状态修改的回归测试验证不可变性；将真正发送的请求快照或可追溯请求哈希与导出样本绑定。历史污染记录保留标记，不能靠新代码补丁自动还原当时输入。

## 3. 日期规则存在上下文冲突

**规则缺陷及具体冲突已确认；部分历史事件日期需重新审阅。**

`frozen_timex.annotation_rule()` 对裸星期词只允许归一化到发布日期之前 0–7 天，不查看句子中的未来时态或相邻显式日期。

例一：Egypt 继承事件 `event-157` 的来源日期为 2012-06-15，引文为“runoff vote set for Saturday and Sunday”，现有事件却记为 **2012-06-09**。程序接受了过去的周六；“set for”所表达的安排并未被规则检查。这不是本轮新生成的错误，仍需审阅原文才能确定最终正确表示。

例二：本次 VERIFY 片段 `1712@6a0fea3a2398:2921:4103` 的元数据日期是 2012-06-15，但正文有 `Thursday, June 21`、`Wednesday, June 20`、`Monday, June 18`，冻结注释却给出 June 14、June 13、June 11。片段内部的显式月日与星期注释相冲突，可能涉及来源更新或原始时间标注问题，不能仅信发布日期锚定。

本轮 Egypt 新增 6 条隔离记录，集中在这类日期/引文校验问题。模型通过改写引文或省略 annotation_id 无法提供可靠修复依据，继续让模型重复修复有低收益风险。

**建议下一版**：显式日期与注释冲突时隔离注释；对未来表达、图片说明和来源更新时间冲突采用单独检查；允许候选保持未知或较粗时间精度，禁止为了通过校验猜具体日。不要把发布日期直接补作事件日期。

## 4. Gap 机制仍会重复提问，也会漏看已有答案

Egypt 最终有 45 个 gap：**24 OPEN、18 DEFERRED、3 RESOLVED**。停止并不是“已无值得检索的问题”。

- `gap-012` 与 `gap-039` 的问题文本完全相同：都询问 2012 年 12 月公投结果，却同时留在队列。
- `gap-015` 已基于 `event-039` 判为 RESOLVED，内容为宪法于 2012-12-26 签署成为法律。
- `gap-043` 又询问官方公投结果与宪法颁行。其复核只看到按词面重合筛选的 12 条事件，没有 `event-039`，因此已有答案未进入复核输入。
- 两个 gap 并非逐字相同、也不能直接认定都完全解决，但现有结案证据至少应复用，避免把已知的颁行部分重新当作空缺。
- 本轮为该 gap 执行 3 条 query，新事件包含 5 月竞选冲突、Facebook 威胁及 12 月反对公投的声明，没有新增 Gold 日期命中。

**建议下一版**：先做规范化问题去重，再做相近问题的证据关联；gap 复核优先带入相关已结案 gap 的证明事件；将多子问题分别标记已知/未知，再生成查询。Gold 仅用于离线评测，不输入控制器制造 gap。

## 5. VERIFY/MERGE 优化确有执行，但尚不能据此判定整体降本和无损

Syria 新轨迹 81 个 VERIFY 步骤中有 10 次抽取缓存复用。排除缓存步骤后，71 个步骤中 12 个标记局部修复成功、6 个标记修复耗尽。全部步骤中的修复耗尽标记为 11，其中包含复用之前耗尽结果的步骤，不能当成 11 次新的修复失败。

Syria 本地删除 2 个确定重复候选：其中 1 个 MERGE 批次完全本地处理，另 1 个仍有候选交给模型。因此“删掉 2 个候选”不等于“少了 2 次 MERGE API 调用”。未完成片段再次被选中、不同分页和相同片段不同抽取状态，都可能导致再次 VERIFY；不能将 81−55 全部视为浪费。

Egypt 新增 38 次 HTTP 中，**FINAL_SELECT 占 21 次（55.26%）**，而 21 页最终没有删除任何事件。其 token 为 19,718/53,972＝36.53%；VERIFY token 为 20,296/53,972＝37.60%。这是接近结束的续跑子段，不代表整个系统的阶段分布，更不是费用比例。

**建议下一版**：在保证最终筛选质量的前提下评估 FINAL_SELECT 的实际增益；记录每批新增证据、新增日期、重复筛除和 gap 进展。无对应费率和账单时保持费用结论未知。

## 6. Memory 和训练数据仍不充分

Egypt 207 条事件最终压缩成 8 条摘要事实，直接引用 13 个不同事件；Syria 107 条事件的 8 条摘要事实引用 12 个不同事件。这是摘要引用范围，不是系统全部可访问事件数；模型还可能看到增量和局部事件。但结合漏看 `event-039` 的实例，说明单靠短摘要和词面局部选择不足以稳定支持 gap 判断。

Egypt 实际记录的最大输入为 3223 tokens，本地估计最大为 3306，未触及 4096 上限。不能只因还有 token 余量就塞入全部历史：应优先改善所需事实的检索与证据索引，保留延迟摘要更新和直接传递事件增量的设计。

训练侧仍缺可验证的自主 STOP 以及覆盖良好的多主题完成轨迹。当前运行成功仅说明执行成功；训练门禁 false 应继续保留，直到输入快照、标签语义和训练/评测拆分审核完成。
